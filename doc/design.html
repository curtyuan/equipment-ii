ii Program Design

ii is a zsh plugin for operator workflow variables stored in the current tmux session. It exposes compact commands for setting, loading, listing, copying, and rendering values into payload text.

Runtime zsh inside tmux, with fzf for interactive selectors.
Shared state tmux session environment variables using the internal ii_ prefix.
Render source current lowercase shell variable first, tmux ii_ fallback second.
Deployment script/make exports a self-contained plugin package under export/ii.

State Model

User command Names are entered without ii_ and are normalized case-insensitively.
tmux session The canonical shared store is ii_name in tmux show-environment.
current shell ii s and ii l export names into the current pane, usually lowercase.
payload renderer Lowercase shell values override tmux for one-command edits.
output Rendered text can be printed, copied, and optionally written to a file.
Core state rules
  • ii_ is an internal tmux namespace, not a user-facing variable name.
  • User names such as RHOST, rhost, and ii_rhost normalize to ii_rhost for storage.
  • Shell exports omit the internal prefix and follow II_EXPORT_CASE: lower, upper, or both.
  • Default names exist as candidates, but empty values are not exported and are hidden from ii ls.
  • Loaded-variable prompt sync can refresh shell values from tmux before the next prompt after ii s or ii l.

Variable Model

Name normalization and matching

User-facing names are case-insensitive. The internal stored name always uses lowercase ii_. This means RHOST, rhost, and ii_rhost all refer to ii_rhost. 

input name: RHOST
normalized tmux name: ii_rhost
default shell export: rhost
Default candidates
domain lhost rhost file lport rport mm user passwd user1 passwd1 hash1 user2 passwd2 hash2

Defaults seed interactive choices. Values only appear in lists or shell exports when they have non-empty tmux values.

List output

ii ls prints each populated variable as a two-line block. The key line is blue in an interactive terminal and there are no blank separator lines. 

lhost
192.168.45.192
lport
443

Clipboard

Configured backend II_CLIP_BACKEND or II_CLIP_CMD wins when explicitly set.
SSH and tmux OSC52 is preferred for SSH-like contexts when base64 is available.
Local X11 xclip-both writes both primary and clipboard selections when available.
Copy boundary

Payload content is passed through stdin whenever possible, not as a tmux command argument. This protects spaces, quotes, shell metacharacters, and HTML-like text. 

print -rn -- "$text" | tmux load-buffer -

Design Risks and Guardrails

Render parser ambiguity

The renderer intentionally consumes lowercase shell-style tokens while preserving uppercase shell tokens and PowerShell scopes. Regression tests should cover mixed input such as $rhost, ${file:t}, $RHOST, $env:TEMP, and combo # stage: metadata emitted as paste-safe comment delimiters.

Shell override priority

A temporary shell assignment such as rhost=1.2.3.4 ii p --input must override tmux for that render. Prompt sync may later refresh shell values from tmux, so this is intentionally a command-scoped override pattern.

Clipboard environment drift

Long-lived tmux sessions may keep stale SSH or display variables. Clipboard backend detection must prefer explicit configuration and local X11 availability where appropriate.

Documentation drift

Live help belongs near command implementation. Markdown and this HTML map should summarize behavior and design, but option registration must stay in the code path that handles the command.
